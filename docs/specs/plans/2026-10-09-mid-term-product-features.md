# FreeLLM 中期产品功能实施计划

> **给代理执行者：** 本计划覆盖 1–2 周的三个独立工作流；实施时每个工作流先补齐对应设计与验收范围，再逐项执行。任务使用 `- [ ]` 跟踪。

**目标：** 在 FreeLLM 静态站点中增加可复制的 Prompt 模板库、改善访客收藏与历史路径，并为 Telegram 和微信反馈渠道预留可核验入口。

**架构要点：** 延续静态 HTML/CSS/JavaScript 与 JSON 数据源；访客收藏和浏览历史继续使用现有浏览器本地存储，GitHub Gist 同步保持可选；反馈渠道只链接到维护者确认的公开账号、群组或二维码，不新增登录、数据库、表单后端或消息采集服务。

**技术栈：** 纯静态站点、原生 JavaScript、JSON 数据、现有 Python 静态构建工具。

**关联设计说明：** 本计划第 1 节记录了已确认范围；Prompt、游客体验和反馈渠道的设计边界分别见第 3、4、5 节。

---

## 1. 已确认范围

1. **Prompt 模板库（第 1 周）：** 首批整理 24 个经审核的模板，支持分类、搜索、详情预览、变量填写和复制；不调用模型 API，不要求用户登录。
2. **游客收藏与浏览历史（第 1 周）：** 保持收藏和历史对游客开放，改善首次使用、空状态、本地保存和可选 GitHub 同步的说明。现有数据默认保存在用户浏览器。
3. **Telegram / 微信反馈渠道（第 2 周）：** 在社区页和关于页增加反馈入口，保留现有邮件入口。只有实际目标地址或二维码已确认且可访问时才显示对应渠道。

本计划只覆盖实施安排，不包含功能代码修改、生产发布、社群创建或替维护者注册社交账号。

## 3. 工作流 A：Prompt 模板库

**初步实现边界：** 使用可审阅的静态模板数据，并新增独立目录页。每个模板至少包含稳定 ID、中文标题/摘要、对应英文标题/摘要、分类、中文提示词正文、中英变量标签与占位说明、双语适用场景、维护日期和来源/归属说明。变量使用明确标记；用户填写变量后在本地预览并复制，不向服务器发送内容。预览内容按纯文本渲染，用户输入中的 HTML 或脚本片段只作为文字显示，不执行。

**建议文件职责（实施设计确认后定稿）：**

- `data/prompt-templates.json`：模板内容与字段。
- `prompts/index.html`：目录、搜索、分类筛选、详情和空状态。
- `js/prompt-library.js`：数据读取、筛选、变量替换与复制交互。
- `css/prompt-library.css`：模板目录的页面样式。
- `js/site-navigation.js`、`scripts/build_static.py` 及 `scripts/build_seo_pages.py`：增加站内发现入口，并让新页面进入静态发布与 sitemap 路径。
- `README.md`：补充新页面入口和内容维护方式。

**验收条件：** 首批 24 个模板可按分类浏览和关键词搜索；变量填写只改写本地预览；HTML 样式输入只作为文本显示且不执行；复制成功与失败都有明确反馈；搜索无结果时仍有清空筛选入口；移动端可操作；所有模板说明用途、变量和来源/归属。模板正文不包含密钥、个人数据或对特定模型效果的无依据承诺。

## 4. 工作流 B：游客收藏与浏览历史

**现状依据：** `js/freellm-sync.js` 已提供本地收藏和历史能力；`favorites/index.html` 已说明本机存储，并将 GitHub Gist 用于跨设备同步。工作重点是路径和说明优化，不重建存储系统。

**计划动作：**

- 梳理首页、资源卡片、收藏页中首次收藏后的提示及入口位置。
- 明确说明访客无需登录即可收藏和查看最近浏览；本地数据只在当前浏览器可用。
- 将 GitHub 连接标注为跨设备同步选项，并说明连接前提；未连接时隐藏会产生“必须登录”误解的提示。
- 在 `js/freellm-sync.js` 中区分“键不存在”与“读取/JSON 解析失败”，并向页面暴露可处理的存储状态；存储读取失败时阻止后续收藏写入用空默认值覆盖原始数据。
- 捕获 `localStorage` 写入异常并向页面反馈；不清空或覆盖已有数据来掩盖错误。

**验收条件：** 未登录用户可以收藏资源、查看最近浏览并刷新后继续访问本地数据；页面没有强制登录拦截；跨设备同步说明准确；存储不可用时给出可理解提示；读取或解析失败的数据不会被空数据覆盖，并保留邮件/站内浏览等其他路径。

## 5. 工作流 C：Telegram / 微信反馈渠道

**实施前置条件：** 维护者提供 Telegram 公开目标（账号、群组或频道）及微信入口（公众号、群组说明页或二维码文件），并确认它们用于接收 FreeLLM 反馈。二维码素材须由维护者提供并确认可公开展示。

**计划动作：**

- 在 `community/index.html` 和 `about/index.html` 呈现可用渠道。当前仓库没有 `contact/` 页面；本计划不新增独立联系页。
- 按“资源纠错 / 推荐新资源 / 一般建议”说明提交时应附的信息，复用现有邮件和提交资源入口。
- 外链采用新窗口时保留安全属性；二维码提供替代文本、旁边可复制的账号/入口文字，以及合适的移动端显示尺寸。
- 微信只有二维码入口时，说明桌面用户可用手机扫码；用户无法使用微信时仍可通过邮件或资源提交页反馈。
- 在渠道说明中提醒不要发送密码、API Key、访问 Token 等凭证。

**验收条件：** 每个展示的渠道均有可访问目标和清楚用途；未配置的渠道不展示；邮件入口继续可用；桌面端可用手机扫码并能读取旁边的账号/入口说明，移动端可以打开链接或识别二维码；无微信用户仍有邮件或资源提交替代渠道；不新增站内收集用户身份或消息的后端。

## 6. 实施顺序与依赖

1. 对模板库补充字段定义、分类、页面交互和内容审核规则；编辑者确认 24 条首批模板及其来源/归属后，完成页面原型评审，再细化页面实施任务。
2. 审阅本地存储与收藏页面现有行为，确定游客提示文案和最小修改范围；单独界定存储异常状态及防止覆盖的处理，再安排页面调整。
3. 收齐并核验 Telegram / 微信入口素材后，细化社区页与关于页变更；二维码入口须有可复制的文字说明和桌面扫码说明。素材未就绪时不添加外链或二维码。
4. 三项工作分别完成后，检查静态构建是否输出新页面、主导航入口和 sitemap 是否包含 `/prompts/`，并人工核对移动端显示、链接可用性和内容准确性。

三个工作流可以独立排期；Prompt 模板库先交付，游客体验改进与内容审核并行准备，反馈渠道等待账号/二维码素材。

## 7. 风险与维护

- **模板质量与版权：** 只收录可说明来源或归属的内容；避免整段复制来源不明的提示词。维护者须能持续核对和更新模板。
- **游客数据边界：** 本地数据可能因清理浏览器而丢失；页面需说明此限制，并把云端同步保持为明确可选项。
- **社区渠道维护：** 新增社交入口会产生维护工作；发布前确认有人定期查看并处理反馈。不能保证响应时间时，不展示响应 SLA。
- **隐私与安全：** 提示词变量在浏览器本地处理；反馈渠道说明不鼓励发送凭证。当前计划不新增用户级跟踪或站内聊天。
